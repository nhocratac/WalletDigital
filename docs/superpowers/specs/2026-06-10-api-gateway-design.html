1.Bối cảnh & Vấn đề

api-gateway là cửa ngõ: mọi request từ người dùng đi qua nó trước khi tới service nghiệp vụ. Nó giải đúng phần "ngoài phạm vi" mà thiết kế wallet nhắc tới: xác thực người dùng và biến danh tính đó thành thông tin đáng tin cho service phía sau. Gateway này không cấp token — token do IdP ngoài cấp.

3.Luồng request (Data Flow)

Authorization: Bearer <JWT>   POST /api/wallets/1/topup
   |
   v [1] JwtAuthFilter — verify chữ ký JWT bằng PUBLIC key
   |       Sai / hết hạn / thiếu  -> 401, CHẶN (không forward)
   v [2] Bóc claims: userId (sub), tenantId
   v [3] RouteTable: "/api/wallets/**" -> http://localhost:8080 (wallet)
   |       Không khớp route -> 404
   v [4] HmacRequestSigner — dựng canonical + ký, GẮN header:
   |       X-Service-Id: api-gateway
   |       X-Timestamp:  <epoch>
   |       X-Signature:  HMAC-SHA256(sharedSecret, canonical)
   |       X-Tenant-Id:  <tenantId từ JWT>     (KHÔNG lấy từ client)
   |       X-Trace-Id:   <truyền tiếp / sinh mới>
   v [5] RestClient forward -> nhận response -> trả client
           Downstream 5xx -> 502 · timeout/không kết nối -> 504

canonical = serviceId + "\n" + method + "\n" + path + "\n" + timestamp + "\n" + sha256(body)
🔑 Hai điểm cốt lõi: (1) Tenant lấy từ JWT, không từ client → người dùng không giả được tenant. (2) canonical + tên header là HỢP ĐỒNG chung với wallet — lệch một ký tự là wallet trả 401. Lý tưởng tách thư viện shared-hmac.

4.Cấu trúc code (Clean Architecture — áp NHẸ)

🔑 Bài học: Giá trị Clean Architecture tỉ lệ với độ phức tạp nghiệp vụ. Gateway gần như không có nghiệp vụ → domain mỏng là ĐÚNG. Chỉ giữ port ở 2 chỗ dễ thay đổi.
com.vng.gateway
├── GatewayApplication.java
├── domain/                          <- MỎNG: value object + 2 port
│   ├── AuthenticatedCaller.java     · userId + tenantId (bóc từ JWT) — thuần Java
│   ├── TokenVerifier.java           · PORT: token -> AuthenticatedCaller (hoặc ném lỗi)
│   └── DownstreamClient.java        · PORT: forward request đã ký -> response
├── application/
│   └── GatewayService.java          · điều phối: verify -> chọn route -> ký -> forward
└── infrastructure/
    ├── security/
    │   ├── JwtAuthFilter.java        · filter CHẶN: gọi TokenVerifier, 401 nếu sai (chạy đầu)
    │   ├── JwtTokenVerifier.java     · ADAPTER cài TokenVerifier (RS256, public key)
    │   └── HmacRequestSigner.java    · dựng canonical + ký — HỢP ĐỒNG chung với wallet
    ├── routing/
    │   ├── RouteTable.java           · map "/api/wallets/**" -> http://localhost:8080
    │   ├── RestClientDownstream.java · ADAPTER cài DownstreamClient (Spring RestClient)
    │   └── ForwardingController.java · controller "bắt tất cả" -> gọi GatewayService
    ├── observability/
    │   └── TraceIdFilter.java        · đảm bảo X-Trace-Id
    └── config/
        └── GatewayProperties.java    · nạp routes + hmac secret + jwt public key từ yml

Hai port = hai chỗ dễ thay đổi: TokenVerifier (đổi IdP/cách verify) và DownstreamClient (đổi RestClient→WebClient, hay sang Spring Cloud Gateway). Đặt port đúng chỗ sẽ thay đổi.

5.JWT/RS256 & HMAC

Tiêu chíHS256 (đối xứng)RS256 (bất đối xứng) ⭐
Khoá1 secret chung ký & verifyIdP giữ private (ký); gateway có public (verify)
Rủi roGateway biết secret → có thể giả tokenGateway không thể tạo token
Phù hợpMột bên vừa ký vừa verifyNhiều service verify, một IdP ký — đúng mô hình

JwtTokenVerifier: tách Bearer token → verify chữ ký (public key) → kiểm exp → (tùy chọn) kiểm issuer/audience → bóc claims → AuthenticatedCaller(userId, tenantId).

🔑 Test khi chưa có IdP: sinh cặp khoá RSA; test helper ký token giả lập bằng PRIVATE key, gateway verify bằng PUBLIC key.
Vì sao RS256 cho JWT nhưng HMAC cho gọi nội bộ? JWT cần "nhiều bên verify, một bên ký" → bất đối xứng. Gọi nội bộ giữa 2 service tin nhau → đối xứng (HMAC) đủ và đơn giản.

6.Xử lý lỗi

Tình huốngHTTP trả clientGhi chú
Thiếu/sai/hết hạn JWT401 UnauthorizedChặn ngay, không forward
Không khớp route404 Not FoundPath không thuộc service nào
Downstream trả 5xx502 Bad GatewayLỗi từ service phía sau
Downstream timeout / không kết nối504 Gateway Timeoutwallet chết/chậm
Lỗi nội bộ gateway500Bug của chính gateway
💡 502/504 chính là chỗ Circuit Breaker thuộc về. Khi downstream liên tục timeout, breaker "mở" để gateway ngừng gọi và trả nhanh 503, tránh dồn request làm sập thêm. Khép lại đúng chỗ đã hoãn lúc thiết kế wallet: gateway là nơi outbound call xuất hiện.

7.Chiến lược kiểm thử

Unit test (nhanh, không mạng):
  · JwtTokenVerifier: hợp lệ -> AuthenticatedCaller đúng; sai chữ ký -> lỗi; hết hạn -> lỗi.
  · HmacRequestSigner: input cố định -> đúng canonical + chữ ký kỳ vọng.
      * KHOÁ hợp đồng với wallet — ai đổi canonical, test đỏ.

Integration test (gateway chạy, downstream GIẢ LẬP bằng MockWebServer/WireMock):
  · * Đầu-cuối: JWT hợp lệ -> verify, ký, forward
       -> MockWebServer nhận đúng X-Tenant-Id (khớp JWT), X-Signature hợp lệ, X-Service-Id.
  · Không có JWT -> 401, MockWebServer KHÔNG nhận gì.
  · Downstream 500 -> 502.   ·   Downstream timeout -> 504.
🔑 Bài học: Giả lập "hàng xóm" (MockWebServer/WireMock) là kỹ năng test sống còn trong microservice — kiểm soát downstream trả gì để test mọi nhánh lỗi, không cần dựng cả hệ thật.

8.Nợ kỹ thuật & YAGNI

Nợ kỹ thuật / để stage sau:

  • Circuit Breaker (Resilience4j) bọc lời gọi downstream — gateway là nơi nó thuộc về.
  • Tách thư viện shared-hmac để gateway & wallet dùng chung buildCanonical().
  • Lấy public key động từ JWKS endpoint của IdP (giờ: nạp tĩnh từ config).

Cố tình chưa làm:

  • Cấp token / login (thuộc IdP/auth-service riêng).
  • Rate limiting, logging nâng cao, nhiều downstream route (giờ chỉ wallet).
  • Chuyển sang Spring Cloud Gateway (sau khi đã hiểu cơ chế).
