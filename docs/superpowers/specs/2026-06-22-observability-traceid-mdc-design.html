🧵 Observability Nấc 1 — TraceId + MDC

📅 2026-06-22 · sợi chỉ traceId xuyên 3 service qua HTTP + Kafka + worker, vào MDC để mọi log tự mang · Nấc 1 (correlation ID); OTel/span = Nấc 2 riêng
Quyết định OB1–OB8 do người học tự suy ra (Socratic). Gateway đã có TraceIdFilter (chưa MDC); wallet/kyc chưa có gì.
1. Vấn đề: sợi chỉ đứt + không vào log · 2. Quyết định OB1–OB8 · 3. Vòng propagation · 4. MDC là gì + bẫy · 5. Phạm vi 3 service

1.Vấn đề

withdraw đi qua 3 service, log rời rạc. Gateway sinh X-Trace-Id rồi forward, nhưng wallet/kyc vứt → đứt chặng đầu; và không ai nhét traceId vào log (chưa MDC).

flowchart LR
    U[User] --> GW["gateway ✅ sinh+forward X-Trace-Id"]
    GW -->|"X-Trace-Id"| W["wallet ❌ vứt, log không traceId"]
    W -->|"gọi kyc — cũng không kèm"| K["kyc ❌"]

2.Quyết định OB1–OB8

#Quyết địnhLý do
OB1Mỗi service có TraceIdFilter: continue-or-generate (UUID) → MDC; chạy SỚM NHẤT (trước HmacVerifyFilter)không phải mọi luồng qua gateway; log 401/lỗi cũng cần traceId
OB2Log pattern [%X{traceId}] ở cả 3 servicemọi dòng log tự mang, khỏi truyền tay
OB3Clear MDC trong finallyThreadLocal — thread tái dùng sẽ rò traceId cũ (bẫy T4)
OB4Outbound HTTP: ClientHttpRequestInterceptor đọc MDC → đính X-Trace-Idmột chỗ cho mọi outbound (RestKycGate/RestBankClient)
OB5Kafka: producer đặt traceId vào HEADER; consumer đọc header → MDCheader = metadata (không nhét payload); nối trace qua async
OB6Worker (không request): sinh traceId mới (root) mỗi vòng → MDC, clear finallykhông upstream → tự sinh như gateway
OB7Format = UUID opaque; KHÔNG nhúng tenantId/userId/PIItraceId đi khắp log/tracing bên thứ 3; nghĩa nhúng vào id sẽ mục + rò PII
OB8Nấc 1 (correlation ID); span/OTel = Nấc 2 riênghand-roll span = tự chế lại OTel; nấc 1 đặt nền propagation

3.Vòng propagation hoàn chỉnh

flowchart TB
    REQ["HTTP request (X-Trace-Id?)"] --> F["TraceIdFilter: đọc/sinh → MDC\n(finally: MDC.clear)"]
    F --> LOG["mọi log [%X{traceId}]"]
    F --> OUT["outbound HTTP: Interceptor MDC → X-Trace-Id header → service kế"]
    F --> PUB["publish Kafka: producer → record HEADER traceId → consumer đọc → MDC"]
    WK["Worker @Scheduled (không request): sinh traceId ROOT → MDC → log → finally clear"]
Đối xứng: mọi điểm DỮ LIỆU ĐI VÀO một thread (HTTP / Kafka / tick đồng hồ) có một chỗ đặt MDC; mọi điểm ĐI RA (HTTP call / Kafka publish) có một chỗ đọc MDC.

4.MDC là gì + bẫy ThreadLocal

sequenceDiagram
    autonumber
    participant T as Thread #7 (pool)
    participant M as MDC (ThreadLocal)
    T->>M: request A → MDC.put(traceId, A)
    Note over T: mọi log.info() → pattern %X{traceId} đọc M → [A] tự chèn
    Note over T: xử lý xong... NẾU KHÔNG clear → trả thread về pool
    T->>M: request B (không header) tái dùng thread #7
    Note over M: MDC vẫn = A 💥 → log của B mang [A] sai
MDC = map key-value gắn theo thread (ThreadLocal) của thư viện log; pattern %X{traceId} đọc nó. Cùng cơ chế + cùng bẫy với TenantContext → set ở filter, clear trong finally, thread không-request tự sinh.

5.Phạm vi 3 service

ServiceHiện cóThêm
gatewayTraceIdFilter (forward, attribute)đưa vào MDC + log pattern
walletkhôngTraceIdFilter→MDC (trước HmacVerifyFilter) + pattern + interceptor outbound + Kafka consumer header→MDC + worker root
kyckhôngTraceIdFilter→MDC + pattern + Kafka producer đặt header
Thứ tự filter wallet (sau Stage 4): TraceIdFilter (sớm nhất) → HmacVerifyFilter @Order(0) → TenantFilter @Order(1) → log cú 401 vẫn có traceId.
