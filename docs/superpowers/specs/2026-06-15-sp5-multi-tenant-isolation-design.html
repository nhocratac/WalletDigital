1.Lỗ hổng: gateway mang tenant tới cửa, wallet vứt đi

Đúng cùng hình lỗ hổng TraceId: gateway gắn, downstream bỏ. Wallet hiện chỉ cô lập theo userId (D2), chưa theo tenant — mọi tenant trộn chung một schema.

2.Tenant ≠ User — hai tầng cô lập

Tenant = khách hàng-tổ chức thuê nền tảng (Shopee, Lazada) chạy chung 1 codebase. User = người dùng cuối BÊN TRONG một tenant.

    B --> T2["Tenant: Lazada"]
    T1 --> U1["users: An, Bình... → ví riêng"]
    T2 --> U2["users: Dũng, Em... → ví riêng"]

3.⭐ Cô lập bằng QUY ƯỚC vs bằng CẤU TRÚC (T1, T2)

Câu hỏi cốt lõi: vì sao schema-per-tenant chứ không phải "1 bảng chung + cột tenant_id + WHERE"?

flowchart TB
    subgraph SHARED["Bảng chung — cô lập bằng QUY ƯỚC (dev phải NHỚ WHERE)"]
        Q1["SELECT * FROM wallet  (quên WHERE tenant_id)"] --> ALL["thấy MỌI tenant 💥"]
    end
    subgraph SCHEMA["schema-per-tenant — cô lập bằng CẤU TRÚC"]
        C["connection → schema 'shopee'"] --> Q2["SELECT * FROM wallet  (quên WHERE)"]
        Q2 --> ONLY["chỉ thấy ví Shopee ✅
bảng tenant khác KHÔNG nằm trong tầm nhìn"]
    end
Insight: bảng chung phụ thuộc dev nhớ thêm WHERE ở MỌI query — 1 lần quên (JOIN, report, dev mới) = lộ toàn bộ. Schema-per-tenant dời ranh giới xuống tầng connection: query trần lỡ quên vẫn vô hại. "Make illegal states unrepresentable." Đáng trả giá nặng vì lộ-chéo tenant = hai công ty cạnh tranh thấy dữ liệu nhau → existential.

4.Routing: Filter → Context → DataSource (T3)

Cùng pattern đã dùng cho X-User-Id và kế hoạch TraceId→MDC. Gateway đã cấp sẵn X-Tenant-Id.

flowchart TB
    REQ["request (X-Tenant-Id: shopee)"] --> F["TenantFilter (chạy sớm)
TenantContext.set('shopee')"]
    F --> CTX[("TenantContext = ThreadLocal")]
    CTX --> R["RoutingDataSource.determineCurrentLookupKey()
đọc TenantContext → 'shopee'"]
    R --> CONN["mở connection vào schema shopee"]
Đọc: dời ranh giới tenant RA KHỎI câu WHERE, xuống tầng mở connection. Hibernate CurrentTenantIdentifierResolver + MultiTenantConnectionProvider (khuyên dùng) hoặc Spring AbstractRoutingDataSource. Thiếu X-Tenant-Id → 400 (không tin client tự khai, như D1).

5.Bẫy chí mạng: ThreadLocal không clear (T4)

Web server tái dùng thread từ pool. Không clear → thread mang context tenant cũ sang request tenant kế → TÁI SINH đúng lỗ hổng lộ-chéo (mà còn khó thấy hơn).

sequenceDiagram
    autonumber
    participant T as Thread #7 (pool)
    participant CTX as ThreadLocal
    T->>CTX: request shopee → set('shopee')
    Note over T: xử lý xong... KHÔNG clear → trả thread về pool
    T->>CTX: thread #7 tái dùng cho request lazada
    Note over CTX: context VẪN 'shopee' 💥
    T->>T: lazada mở connection vào schema SHOPEE → thấy/ghi nhầm dữ liệu shopee
Quy tắc: ThreadLocal set ở đâu clear ở đó, trong finally — kể cả request ném exception. try { TenantContext.set(t); chain.doFilter(); } finally { TenantContext.clear(); }. Áp y hệt cho MDC traceId. Bẫy này test 1 request luôn đúng, chỉ vỡ khi tải cao (thread tái dùng) — cực khó truy.

6.Master registry — vì sao cần chỗ chung (T5)

Chicken-and-egg: routing phải tra map tenantId→schema TRƯỚC khi vào bất kỳ tenant nào.

flowchart LR
    A["muốn vào schema tenant X"] --> B["phải biết X tồn tại + schema tên gì"]
    B --> C["map đó đọc ở đâu?"]
    C -->|"nếu cất TRONG schema tenant"| D["phải VÀO schema mới đọc được 🔄"]
    D --> A
Kết luận: phải có master schema (không thuộc tenant nào) giữ tenant_registry(tenant_id, schema_name, status) — đọc được trước khi routing. schema-per-tenant ≠ MỌI thứ per-tenant: dữ liệu VỀ tenant (danh bạ) tách khỏi dữ liệu CỦA tenant (ví/ledger/order). Worker cũng cần danh bạ này để lặp; provisioning ghi tenant mới trước khi schema của nó tồn tại.

7.Provisioning (eager) + Flyway (T6, T7)

Tạo schema lúc ĐĂNG KÝ tenant (onboarding), không lazy lúc request đầu — để user thật không phải chờ dựng schema.

flowchart TB
    NEW["POST /admin/tenants {globex}"] --> R1["1. INSERT registry(globex, PROVISIONING)"]
    R1 --> R2["2. CREATE SCHEMA tenant_globex"]
    R2 --> R3["3. flyway.migrate(tenant_globex) → V1..Vn"]
    R3 --> R4["4. status = ACTIVE"]
    R3 -->|lỗi| RF["status = MIGRATION_FAILED (không ACTIVE nửa vời)"]

Flyway = "git cho cấu trúc DB": versioned SQL + history table mỗi schema → mọi schema hội tụ cùng hình dạng.

flowchart TB
    NEWS["tenant mới (schema rỗng)"] -->|flyway migrate| F1["chạy V1→V4 từ đầu → cấu trúc CHUẨN ✅"]
    OLDS["tenant cũ (đang V3)"] -->|flyway migrate| F2["chỉ chạy V4 còn thiếu → cũng CHUẨN ✅"]
Bài học: MỘT bộ file V duy nhất là nguồn sự thật cho cấu trúc; cũ-mới đều chạy qua cùng chuỗi → không thể lệch cột. Mỗi V chạy đúng một lần (history table).

8.Fleet migration + Expand/Contract (T8)

Chạy V mới lên N schema đang sống — KHÔNG nguyên tử được (như "khe hở" phân tán SP3). Hai vũ khí.

flowchart TB
    J["Migration job: lặp registry (ACTIVE)"] --> L{từng tenant}
    L --> OK1["shopee → V5 ✅"]
    L --> ERR["tenant #37 → LỖI ❌ (status=MIGRATION_FAILED, KHÔNG chặn tenant khác)"]
    L --> OK2["tiki → V5 ✅"]
    ERR --> RT["chạy lại job → Flyway bỏ qua cái đã xong, retry #37; lỗi dai → ops (như NEEDS_MANUAL_REVIEW SP4)"]

Vũ khí 2 — làm mixed-version AN TOÀN: rename owner_name → display_name = 5 bước, KHÔNG RENAME một phát.

flowchart LR
    A["1. EXPAND: add display_name (nullable)"] --> B["2. DUAL-WRITE cả hai (đọc owner_name)"]
    B --> C["3. BACKFILL owner_name→display_name"]
    C --> D["4. SWITCH READ sang display_name"]
    D --> E["5. CONTRACT: drop owner_name"]
Bài học: một thay đổi "phá vỡ" = chuỗi thay đổi "chỉ-thêm" tương thích ngược. Tại mọi thời điểm code chỉ cần MỘT cột và cột đó luôn có dữ liệu đúng → tenant V_cũ & V_mới cùng chạy. Tách deploy-schema và deploy-code; chỉ xóa cũ khi chắc không ai dùng. (zero-downtime)

9.SP4 worker đa-tenant (T9)

Reconciliation worker chạy trên thread @Scheduled — không request, không filter → phải tự lặp registry + set context per tenant.

flowchart TB
    W["@Scheduled reconcileAllTenants()"] --> L{lặp registry ACTIVE}
    L --> S["TenantContext.set(tenant)"]
    S --> R["reconcile orders trong schema tenant đó"]
    R --> C["TenantContext.clear() — finally!"]
    C --> L
Đọc: orders mỗi tenant ở schema khác nhau → không thể quét một phát. Reviewer SP4 đã chạm bản nhẹ ("isolate scheduler context from shared H2", commit 29751a9); SP5 tổng quát hóa. Webhook bank chạy trên request-thread nên có context bình thường (bank gửi tenant / bankRef mã hóa tenant).
