1.Kiến trúc tổng thể

Ai gọi ai, đồng bộ (mũi tên đặc) vs bất đồng bộ qua Kafka. Gateway xác thực người dùng; mỗi service tin nhau qua HMAC.

    CO(["Compliance"]) -->|JWT role=compliance| GW
    V(["Verifier bên thứ 3"]) -->|webhook + HMAC verifier| K["kyc-service :8082"]
    GW -->|HMAC + X-User-Id| W["wallet-service :8080"]
    GW -->|HMAC + X-Roles| K
    W -->|"sync GET status
(breaker + cache)"| K
    K -.->|publish kyc.revoked| KB[("Kafka
kyc.revoked")]
    KB -.->|consume| W
    W --> WDB[("Wallet DB")]
    K --> KDB[("KYC DB")]
Đọc: nét đặc = gọi đồng bộ (REST). Nét đứt = bất đồng bộ (event Kafka). Để ý wallet gọi kyc đồng bộ (hỏi status lúc rút) NHƯNG nhận revoke bất đồng bộ — hai chiều, hai cơ chế.

2.Tạo ví & định danh user (D1)

JWT không bao giờ tới wallet. Gateway bóc userId từ claim, gắn vào header đã ký. Wallet tin header vì chữ ký HMAC, không tin client.

sequenceDiagram
    autonumber
    actor U as Người dùng
    participant GW as api-gateway
    participant W as wallet-service
    participant DB as Wallet DB
    U->>GW: POST /api/wallets + JWT
    GW->>GW: verify JWT (RS256) bằng public key
    GW->>GW: bóc claim sub -> userId
    GW->>W: POST /wallets + X-User-Id=A + X-Signature
    W->>DB: lưu ví gắn userId=A (balance 0)
    W-->>U: 201 wallet
Bài học: client gửi userId trong body thì user A mạo danh user B được. Lấy từ JWT (gateway đã verify) là nguồn DUY NHẤT đáng tin.

3.KYC — xác minh bất đồng bộ (SP2)

Nộp hồ sơ xong KHÔNG biết khi nào duyệt xong → verifier chủ động gọi webhook báo kết quả (Hollywood principle: "đừng gọi tôi, tôi gọi anh").

sequenceDiagram
    autonumber
    actor U as Người dùng
    participant GW as api-gateway
    participant K as kyc-service
    participant V as Verifier (bên thứ 3)
    participant DB as KYC DB
    U->>GW: POST /kyc/submissions (giấy tờ) + JWT
    GW->>K: forward + X-User-Id + HMAC
    K->>DB: lưu KycSubmission (bất biến), case = PENDING
    K->>V: đẩy hồ sơ đi xác minh
    K-->>U: 201 submissionId (đang PENDING)
    Note over V: duyệt (auto / người) — vài phút đến vài giờ
    V->>K: POST /kyc/webhooks/decision + HMAC (secret RIÊNG verifier)
    K->>K: WebhookAuthFilter verify chữ ký verifier
    alt đã có decision cho submission (verifier retry)
        K-->>V: 200 DUPLICATE_IGNORED
    else submission lạc hậu (user đã nộp lại)
        K-->>V: 200 STALE_IGNORED
    else hợp lệ
        K->>DB: ghi KycDecision + case PENDING -> APPROVED/REJECTED
        K-->>V: 200 APPLIED
    end
Bài học: webhook luôn trả 200 cho trùng/lạc hậu — vì 4xx khiến verifier retry vô hạn. Mã HTTP ở webhook là tín hiệu điều khiển retry của đối tác.

4.⭐ Withdraw qua cổng KYC (SP3 — luồng trung tâm)

Gộp mọi quyết định: idempotency → AuthZ ví → cổng KYC NGOÀI transaction (cache + breaker, fail-closed) → transaction trừ tiền. Theo dõi các nhánh rẽ.

sequenceDiagram
    autonumber
    actor U as Người dùng
    participant GW as api-gateway
    participant W as wallet-service
    participant C as Cache (Caffeine)
    participant CB as CircuitBreaker
    participant K as kyc-service
    participant DB as Wallet DB
    U->>GW: POST /api/wallets/7/withdraw + JWT + Idempotency-Key
    GW->>W: forward + X-User-Id=A + HMAC
    Note over W: [0] Idempotency replay (ngoài tx)
    alt key đã tồn tại
        W-->>U: trả bút toán CŨ (KHÔNG gọi KYC)
    else key mới
        Note over W: [1] Scoped load ví 7 theo userId A
        alt ví 7 không thuộc A
            W-->>U: 404 + audit log nội bộ
        else ví hợp lệ
            Note over W,K: [2] CỔNG KYC — NGOÀI transaction (D4)
            W->>C: có APPROVED(A) trong cache?
            alt cache hit
                C-->>W: APPROVED
            else cache miss
                W->>CB: check(A)
                alt breaker MỞ
                    CB-->>W: fail-fast (không gọi KYC)
                    W-->>U: 503 + Retry-After
                else breaker đóng
                    CB->>K: GET /kyc/cases/A/status + HMAC
                    alt APPROVED
                        K-->>W: APPROVED
                        W->>C: ghi cache APPROVED(A)
                    else PENDING / REJECTED / REVOKED
                        K-->>W: trạng thái khác
                        W-->>U: 403 + status
                    end
                end
            end
            Note over W,DB: [3] TRANSACTION (ngắn, không network)
            W->>DB: trừ tiền + ghi ledger (cùng 1 tx)
            DB-->>W: commit
            W-->>U: 200 TransactionResponse
        end
    end
Bài học: cú gọi KYC nằm NGOÀI transaction (D4 — tránh giữ connection pool khi gọi mạng). Breaker mở + cache hit vẫn rút được = "cache thoát hiểm" khi KYC chết. 503 (không kiểm được) khác 403 (không đủ điều kiện).

5.Revoke → Kafka → evict cache + compensation (D5, D9)

Compliance thu hồi KYC → phát event bền qua Kafka → wallet xoá cache (chặn rút tiếp) + quét ledger tìm giao dịch lọt khe.

sequenceDiagram
    autonumber
    actor CO as Compliance
    participant GW as api-gateway
    participant K as kyc-service
    participant KB as Kafka (kyc.revoked)
    participant W as wallet-service
    participant C as Cache
    participant L as Wallet Ledger
    CO->>GW: POST /kyc/cases/A/revoke + JWT(role=compliance)
    GW->>K: forward + X-Roles=compliance + HMAC
    K->>K: kiểm role compliance (AuthZ, không chỉ AuthN)
    K->>K: case APPROVED -> REVOKED + ghi KycDecision
    K->>KB: publish kyc.revoked (key=A, acks=all)
    K-->>CO: 200
    Note over KB,W: Kafka GIỮ event — wallet chết rồi sống lại vẫn nhận (offset)
    KB->>W: deliver kyc.revoked
    W->>C: evict(A) — tự nhiên idempotent, trùng vô hại
    W->>L: quét WITHDRAW của A sau revokedAt
    alt có giao dịch nghi vấn (lọt khe)
        W->>W: log COMPENSATION-ALERT (detect & compensate)
    end
Bài học: khe hở "revoke đuổi không kịp withdraw" là bản chất hệ phân tán, không triệt tiêu được — chỉ thu nhỏ (event) + bù (compensation từ ledger). "Xoá cache" tự nhiên idempotent nên consumer KHÔNG cần dedup.

6.KYC State Machine

Luật chuyển trạng thái ép TRONG domain KycCase — mọi mũi tên KHÔNG vẽ ở đây đều bị InvalidKycTransitionException chặn (ma trận test 20 ô).

stateDiagram-v2
    [*] --> NOT_STARTED
    NOT_STARTED --> PENDING: submit
    REJECTED --> PENDING: submit (nộp lại)
    REVOKED --> PENDING: submit (nộp lại)
    PENDING --> APPROVED: approve (webhook)
    PENDING --> REJECTED: reject (webhook)
    APPROVED --> REVOKED: revoke (compliance)
    note right of APPROVED: chỉ trạng thái này
wallet cho rút tiền
Bài học: "make illegal states unrepresentable" — vd REJECTED không thể nhảy thẳng APPROVED (phải submit lại → PENDING → approve). Bug compliance hay nằm ở transition lẽ ra bị cấm mà lại đi được.

7.Idempotency Race Recovery (ca hiếm nhất)

Hai request cùng key đua nhau. UNIQUE(key) ở DB là trọng tài. Nhánh dưới là ca "người thắng cũng rollback".

sequenceDiagram
    autonumber
    participant T1 as Request 1 (key k1)
    participant T2 as Request 2 (key k1)
    participant DB as DB UNIQUE(key)
    par hai request đua đồng thời
        T1->>DB: INSERT bút toán k1
        T2->>DB: INSERT bút toán k1
    end
    DB-->>T1: OK (thắng cú INSERT)
    DB-->>T2: DataIntegrityViolation (thua)
    Note over T2: recovery — đọc lại bút toán k1
    alt T1 đã commit thành công
        T2->>DB: SELECT k1
        DB-->>T2: bút toán của T1
        T2->>T2: payload khớp -> trả 200 / lệch -> 409
    else T1 CŨNG rollback (đụng @Version, rớt kết nối...)
        T2->>DB: SELECT k1
        DB-->>T2: RỖNG (bút toán T1 đã bốc hơi)
        T2->>T2: ném lại DIVE -> 409 "retry được"
    end
Bài học: "thắng cú INSERT" ≠ "commit thành công". Recovery cũng có thể thất bại — và nhánh thất-bại-của-recovery cũng phải có câu trả lời tử tế (409 thay vì 500 thô).
