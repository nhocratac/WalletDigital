1.Bối cảnh & Vấn đề

Yêu cầu gốc R1: user phải KYC APPROVED mới được RÚT; nhận/nạp tự do. SP1 cho wallet lệnh withdraw, SP2 cho kyc-service trả lời status. SP3 nối hai mảnh — và phát hiện wallet thiếu nền tảng định danh: ví không gắn user (chỉ có ownerName — tên hiển thị, không phải khoá) → (a) không có gì để hỏi KYC, (b) lỗ hổng IDOR: ai cũng rút được từ bất kỳ ví nào nếu đoán đúng id.

Người dùng ──JWT──► [api-gateway] ──HMAC + X-User-Id──► [wallet-service]
                                                            │   ▲
                          GET /kyc/cases/{u}/status (sync,  │   │ cache APPROVED (TTL ngắn)
                          circuit breaker, timeout 2s)      ▼   │
                                                        [kyc-service]
                                                            │ publish khi compliance revoke
                          Kafka topic kyc.revoked           │
                [wallet consumer] ◄─────────────────────────┘
                xoá cache + quét ledger compensation

3.Định danh & Sở hữu (sửa IDOR)

  • Bảng wallet thêm user_id NOT NULL; Wallet.createNew(userId, ownerName); controller đọc X-User-Id.
  • Port đổi: findById(id) → findByIdAndUserId(id, userId) — áp cho cả 4 endpoint (GET ví, topup, withdraw, transactions) vì IDOR hở ở tất cả.
  • Không khớp → WalletNotFoundException (cùng 404 với "không tồn tại") + log AUDIT forbidden-or-missing wallet access: walletId, callerUserId, traceId.
⚠️ Giả định tin cậy (nợ tường minh): X-User-Id hiện được wallet tin mà CHƯA verify HMAC (wallet chưa có InternalAuthFilter — Stage 4 của thiết kế gốc). Biên tin cậy tạm = mạng nội bộ + gateway là cửa duy nhất. Stage 4 mới đạt chuẩn zero-trust.

4.Luồng withdraw mới & ranh giới transaction

POST /wallets/7/withdraw  (X-User-Id: user-A, Idempotency-Key: k1, amount 50)
   ▼ [0] Idempotency check (Stage 2): key đã có -> trả bút toán cũ, DỪNG
   ▼ [1] Scoped load: ví 7 thuộc user-A?   không -> 404 + audit log
   ▼ [2] ═══ CỔNG KYC — NGOÀI transaction ═══
   │     cache APPROVED?  có -> qua cổng (không network)
   │     không -> GET /kyc/cases/user-A/status (breaker, timeout 2s)
   │          APPROVED -> ghi cache -> qua cổng
   │          khác     -> 403
   │          breaker mở / timeout / 5xx -> 503 + Retry-After (fail-closed)
   ▼ [3] ═══ TRANSACTION DB (ngắn, không network) ═══
   │     load ví (scoped) -> withdraw(50) -> save (@Version) -> ghi ledger
   ▼ [4] commit -> response
⚠️ Bẫy Spring self-invocation: gọi method @Transactional từ TRONG cùng class thì proxy không kích hoạt — transaction âm thầm không tồn tại. Giải pháp đề xuất: TransactionTemplate (tường minh) hoặc tách bean ledger riêng. Bài học: ranh giới transaction là quyết định thiết kế, không phải chỗ tiện thì dán annotation.

⚠️ Bẫy multi-instance: Caffeine là cache per-instance. N instance chung MỘT consumer group → Kafka giao event revoke cho MỘT instance → N-1 còn lại ôm cache cũ tới hết TTL! Lối thoát khi scale: (a) consumer group id riêng mỗi instance (broadcast — chọn làm mặc định, rẻ) hoặc (b) Redis dùng chung. SP3 chạy 1 instance nhưng code theo (a) sẵn.

Circuit Breaker (Resilience4j) — đề xuất để duyệt

Tham sốGiá trịNghĩa
slidingWindowSize / failureRateThreshold10 / 50%≥5/10 lỗi gần nhất → MỞ

Fail-closed có cache thoát hiểm: breaker mở ≠ chặn tất cả — user APPROVED còn cache vẫn rút được (thu nhỏ bán kính nổ, đúng lời giải "KYC chết thì sao").

7.Compensation — quét ledger khi nhận revoke (D5)

1. cache.evict(userId)                       ← chặn rút TIẾP THEO ngay
2. tìm các ví của userId
3. ledger WHERE type=WITHDRAW AND created_at >= revokedAt
4. nếu có -> log WARN "COMPENSATION-ALERT userId=... suspiciousWithdrawals=[...]"

Scope SP3: phát hiện + cảnh báo. Đóng băng ví / bút toán đảo / báo cáo compliance = YAGNI có chủ đích.

10.Nợ kỹ thuật & YAGNI

NỢ — có điều kiện tái xét

  • X-User-Id chưa verify HMAC tại wallet → wallet Stage 4.
  • Thư viện shared-hmac (canonical đã lặp ở 3 nơi).
  • Transactional outbox cho producer.
  • Redis thay Caffeine khi nhiều instance (hoặc group-per-instance đã chọn sẵn).

YAGNI — cố tình không làm

  • Compensation tự động (freeze/reversal) — chỉ log alert.
  • Dead-letter topic; KYC tiers; gate cho topup (R1: nạp tự do); backfill user_id.
